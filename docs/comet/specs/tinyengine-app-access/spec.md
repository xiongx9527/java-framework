# TinyEngine 应用访问范围

## 目标

TinyEngine 应根据当前真实用户在每个应用上的有效角色关系返回应用列表并限制应用操作。应用中心应为有权角色提供成员管理入口；框架内置的 `system` 技术上下文继续支持未启用认证时的租户级默认行为。

## 应用角色

- 系统应以 `t_permission_role.code` 识别应用角色，稳定代码分别为 `app_owner`、`app_admin`、`app_dev`。
- 三种角色的 `role_type` 均应为 `app`。
- 每个应用最多存在一个 `app_owner` 关系。
- 用户与应用角色关系应存储在 `r_auth_users_units_roles`，其中 `unit_type` 为 `app`，`unit_id` 为应用 ID，`user_id` 为用户 ID，`role_id` 指向对应角色。
- 仅 `expired_time` 为空或晚于当前数据库时间的关系有效。

## 应用列表可见性

- 对真实用户，应用分页列表只应返回当前租户内、该用户持有有效 `app_owner`、`app_admin` 或 `app_dev` 关系的应用。
- 按设计器 ID 查询应用列表应遵循相同规则，并继续应用设计器 ID 条件。
- 用户没有应用关系、关系角色不是三种应用角色或关系已过期时，不应返回对应应用。
- 超级管理员、组织管理员、设计器管理员和其他非应用角色不应自动绕过应用列表过滤。
- 分页总数应使用与列表相同的租户、用户角色和请求查询条件。
- 当前真实用户 ID 缺失时，可见应用集合应为空。
- 当前上下文是框架内置 `system` 技术身份时，应保留当前租户内的既有列表行为，不要求数据库角色关系。

## 应用操作权限矩阵

- `app_owner` 应能读取、更新应用管理配置、开发编辑与保存、预览、发布和删除对应应用。
- `app_admin` 应能读取、更新应用管理配置、开发编辑与保存、预览和发布对应应用，但不能删除应用。
- `app_dev` 应能读取、编辑与保存既有开发资源、预览对应应用，但不能新增模型、更新应用管理配置、发布或删除应用。
- 应用管理配置应包括应用元数据和应用扩展配置。
- 开发编辑与保存应包括页面、区块、既有模型、数据源、资源、国际化、画布保存及现有同类应用内开发能力。
- 新增模型只应允许 `app_owner`、`app_admin`；`app_dev` 新增模型时应返回权限不足且不写入数据。
- 页面与区块锁定/解锁按独立的现有互斥规则处理，三种应用角色均可使用。
- 用户执行无权操作时，系统应返回统一的权限不足结果，且不得产生部分数据变更。
- 角色授权应在 Core 服务边界执行，并由 Servlet MVC、WebFlux 和其他服务调用路径共享，不能仅依赖 Controller 检查。
- 授权应同时校验当前租户、应用 ID、用户 ID、角色代码和角色有效期。

## 应用成员角色管理

- 系统应同时提供 Servlet MVC 与 WebFlux 后端 API，用于查询应用成员角色、分配或变更角色以及移除角色。
- 对应应用的 `app_owner` 和 `app_admin` 可以调用应用成员角色管理 API。
- 成员查询应返回应用成员的用户标识、账号信息、角色代码和角色有效期等现有关系信息。
- `app_owner` 或 `app_admin` 只能为当前租户内的其他用户分配或变更 `app_admin`、`app_dev`，不得对自己的角色关系执行新增、变更或移除。
- 同一用户在同一应用上最多存在一个 `unit_type = 'app'` 的关系。
- 首次分配与角色变更应为不同操作；用户已有该应用角色关系时，重复新增应被拒绝且不得覆盖原角色，角色调整必须使用明确的变更操作。
- 成员角色关系被移除后，可以重新为该用户分配当前应用的 `app_admin` 或 `app_dev`。
- 移除 `app_admin` 或 `app_dev` 后，新的列表可见性和应用操作权限应立即生效。
- 成员管理 API 不应允许任何调用者分配、变更或删除 `app_owner`，也不提供 Owner 转让或多 Owner 能力。
- Owner 唯一性应在持久化边界强制执行并覆盖并发写入，任何产生第二个 `app_owner` 的操作都应失败且保留原 Owner。
- `app_dev`、无应用角色用户和跨租户用户调用成员管理 API 时应返回权限不足，且不得产生部分数据变更。
- 成员角色管理的授权与写入应在 Core 服务边界完成，MVC 与 WebFlux 只负责协议适配。

## 应用中心成员入口

- 应用中心卡片视图和表格视图的每个应用操作区都应提供可发现的“成员管理”入口。
- 入口只对该应用的 `app_owner`、`app_admin` 显示；`app_dev` 和无应用角色用户不应看到入口。
- 前端入口可见性所需的当前用户应用角色应来自后端可信数据，不应根据创建人名称等展示字段推断。
- 成员管理应使用独立对话框，展示成员账号或用户标识及应用角色，不跳转到新的应用中心页面。
- 对话框应支持添加成员、把其他非 Owner 成员在 `app_admin` 与 `app_dev` 之间变更、移除其他非 Owner 成员。
- Owner 行、当前操作者行及不允许的操作应隐藏或禁用；前端保护不得替代后端权限校验。
- 添加、修改或移除成功后只应刷新当前应用的成员列表，不刷新整个应用中心页面。
- 成员列表加载失败时应保留对话框和入口，并提供重试能力。
- 重复成员、操作自己、Owner 保护、越权和跨租户错误应显示明确业务消息；业务 403 不应自动清除 TinyEngine 登录状态。

## 应用创建者关系

- 真实用户成功创建应用时，系统应为其创建该应用的 `app_owner` 关系。
- 真实用户创建应用时应产生且仅产生一个 `app_owner`；已有 Owner 时不得再写入第二条 Owner 关系。
- 应用、默认首页和所有者关系应在同一事务中完成；任何一步失败时全部回滚。
- 技术性的 `system` 身份创建应用时，不要求写入真实用户角色关系。

## 应用删除关系清理

- 删除应用成功时，系统应删除该应用在 `r_auth_users_units_roles` 中的全部应用级用户角色关系。
- 关系清理应同时匹配当前租户、应用 ID 和 `unit_type = 'app'`，不得删除同一用户或同一 ID 对应的其他业务单元关系。
- 应用页面、应用本身和应用角色关系的删除应位于同一事务；任何一步失败时全部回滚。
- 只有 `app_owner` 可以删除应用；本节同时约束删除后的关联数据一致性。

## 页面与区块锁定

- `app_owner`、`app_admin`、`app_dev` 均可对其有权访问的应用发起页面或区块锁定与解锁。
- 锁定与解锁应保持现有占用者互斥规则：用户不能抢占其他用户持有的锁，且只有当前占用者可以解锁。
- 三种应用角色之间不应对锁定与解锁增加额外权限差异。

## 数据初始化与升级

- MySQL 与 H2 初始化数据应提供三种唯一应用角色代码。
- 升级脚本应将既有应用管理员、应用开发者角色规范为 `app_admin`、`app_dev`，并增加 `app_owner`。
- 升级脚本应为历史应用创建者回填 `app_owner`，但仅限该创建者尚无同一应用的任何应用级角色关系时。
- 初始化和升级操作应可重复执行，不产生重复角色或重复用户-应用关系。

## 兼容性

- Servlet MVC 与 WebFlux API 应共享同一 Core 查询和成员管理语义。
- 现有查询参数、响应结构、排序和分页上限保持兼容；新增可信角色字段应保持向后兼容。
- 实现应兼容 Java 8。
