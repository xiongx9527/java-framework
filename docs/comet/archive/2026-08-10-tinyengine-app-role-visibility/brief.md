# Outcome

TinyEngine 应用列表只向与应用存在有效 `app_owner`（应用创建者）、`app_admin`（应用管理者）或 `app_dev`（应用开发者）角色关系的真实用户展示对应应用，并根据角色限制对应应用的操作能力，同时确保新建应用和历史应用具备可用的所有者关系。

# Scope

- 在应用分页列表和按设计器查询的应用列表中，按当前用户的应用级角色关系过滤结果。
- 使用 `t_permission_role.code` 中的 `app_owner`、`app_admin`、`app_dev` 作为三种应用角色的稳定标识。
- 应用分页总数与列表采用相同的用户可见范围，避免通过总数泄露不可见应用。
- 创建应用成功时，为创建者建立该应用的 `app_owner` 关系。
- 删除应用成功时，删除该应用对应的全部应用级用户角色关系。
- 为 MySQL、H2 的初始化/升级脚本补齐三种角色代码，并为没有应用级关系的历史应用创建者回填所有者关系。
- 保持 Servlet MVC 与 WebFlux 两套应用列表 API 的行为一致。
- 按应用角色对应用读取、开发、管理、发布和删除等操作实施一致的服务层授权。
- 新增应用成员角色管理后端 API，由 `app_owner` 或 `app_admin` 查询成员并分配、变更或移除 `app_admin`、`app_dev`。

# Non-goals

- 不在本变更中实现应用成员角色管理控制台界面。
- 不提供应用 owner 转让、多 owner 或通过成员 API 修改 owner 关系的能力。
- 不改变租户隔离、应用模板列表或平台列表的既有行为。
- 不允许超级管理员、组织管理员或其他非应用角色自动绕过真实用户的应用列表过滤。

# Acceptance examples

- A1：真实用户在某应用上具有有效 `app_owner` 关系时，分页列表和对应设计器的应用列表均包含该应用。
- A2：真实用户在某应用上具有有效 `app_admin` 或 `app_dev` 关系时，分页列表和对应设计器的应用列表均包含该应用。
- A3：真实用户没有该应用关系、关系角色不属于三种应用角色，或关系已过期时，两个应用列表均不包含该应用。
- A4：分页接口的 `total` 只统计当前用户可见且满足查询条件的应用，并与分页数据使用同一可见范围。
- A5：真实用户创建应用成功后，系统同时建立该用户、该应用和 `app_owner` 角色之间的有效关系；关系建立失败时应用创建整体失败并回滚。
- A6：数据库初始化/升级后存在唯一代码为 `app_owner`、`app_admin`、`app_dev` 的应用角色；已有应用在创建者尚无应用级关系时获得 `app_owner` 回填，因此创建者仍可看到其应用。
- A7：框架未启用认证而使用内置 `system` 技术上下文时，应用列表继续按当前租户返回，避免默认无认证模式退化为空列表。
- A8：删除应用成功时，该应用在 `r_auth_users_units_roles` 中 `unit_type = 'app'` 的全部角色关系同时删除；角色关系清理失败时应用删除整体失败并回滚。
- A9：`app_owner`、`app_admin`、`app_dev` 均可按现有机制锁定和解锁页面或区块；系统继续禁止抢占他人的锁，并且只允许当前占用者解锁。
- A10：`app_owner` 可读取、更新应用管理配置、开发编辑与保存、预览、发布和删除对应应用。
- A11：`app_admin` 可读取、更新应用管理配置、开发编辑与保存、预览和发布对应应用，但删除应用时被拒绝且数据不发生变化。
- A12：`app_dev` 可读取、编辑与保存既有开发资源、预览对应应用，但不能新增模型，也不能更新应用管理配置、发布或删除应用；被拒绝时数据不发生变化。
- A13：应用角色授权在 Core 服务边界生效，Servlet MVC、WebFlux 及直接服务调用对无权限操作均返回统一的权限不足结果，不能通过非 Controller 调用绕过。
- A14：`app_owner` 或 `app_admin` 可通过 MVC 与 WebFlux API 查询对应应用的成员及角色，并为尚无该应用角色的同租户用户分配 `app_admin` 或 `app_dev`；同一用户重复新增时被拒绝且不覆盖原角色。
- A15：`app_owner` 或 `app_admin` 可明确变更或移除其他成员的 `app_admin`、`app_dev`；变更后权限立即生效，移除后若无有效关系则应用从该用户列表消失且应用操作被拒绝。
- A16：成员管理者不能新增、变更或移除自己的角色；`app_dev`、无应用角色用户和跨租户用户不能管理成员；任何调用者都不能通过成员 API 分配、变更或删除 `app_owner`，失败时不产生部分数据变更。
- A17：每个应用最多存在一个 `app_owner`；真实用户创建应用及历史 owner 回填均只产生唯一 owner，任何产生第二个 owner 的写入都被拒绝且不改变现有关系。

# Constraints and invariants

- 保持 Java 8 兼容，不引入 Java 9+ API。
- 用户、应用、角色关系复用 `r_auth_users_units_roles`；应用关系使用 `unit_type = 'app'`、`unit_id = app.id`。
- 角色有效期为 `expired_time IS NULL` 或晚于当前数据库时间。
- 所有查询继续受当前 `tenant_id` 约束，不能跨租户返回应用。
- 当前用户 ID 缺失且不是内置 `system` 上下文时，真实用户可见应用集合为空。
- 数据升级应幂等，不能覆盖已有的应用管理员或开发者关系。
- 删除应用角色关系时必须同时匹配当前租户、应用 ID 和 `unit_type = 'app'`，不能误删其他业务单元关系。
- 角色授权应先验证当前租户与应用归属，再验证未过期的应用角色，不能跨租户授权。
- 成员角色管理目标用户必须属于当前租户；同一用户在同一应用上最多保留一个应用角色关系。
- 成员角色新增与角色变更是不同操作；新增发现已有关系时必须拒绝，不能隐式覆盖。
- 每个应用最多一个 `app_owner`；owner 唯一性校验必须覆盖并发写入，不能只依赖调用方约定。

# Decisions

- 三种角色使用用户指定的稳定代码 `app_owner`、`app_admin`、`app_dev`；显示名称可保留 TinyEngine 既有命名风格。
- 权限过滤放在 Core 应用服务/Mapper 查询边界，使 MVC、WebFlux 和后续复用方获得一致结果。
- 应用创建与所有者关系写入处于同一事务中。
- 应用删除与该应用全部角色关系清理处于同一事务中。
- 历史数据只为尚无该用户-应用关系的创建者补 `app_owner`，已有 `app_admin` 或 `app_dev` 关系保持不变。
- `system` 是框架技术身份而非真实用户，保留租户级可见性；其他真实用户没有三种角色时不返回应用。
- 页面与区块锁定/解锁不按三种应用角色进一步区分，保持当前占用者互斥语义。
- 采用分层权限矩阵：`app_owner` 拥有全部应用操作；`app_admin` 除删除外拥有读取、应用管理配置、开发保存、预览和发布权限；`app_dev` 仅拥有读取、既有开发资源编辑保存和预览权限。
- 应用管理配置包括应用元数据及应用扩展配置；开发保存包括页面、区块、既有模型、数据源、资源、国际化和画布保存等现有应用内开发能力。新增模型仅允许 `app_owner`、`app_admin`。
- 权限判断集中在 Core 服务边界，Web 层保持 MVC 与 WebFlux 的一致响应映射。
- 应用成员角色管理允许 `app_owner` 和 `app_admin`；可管理的目标角色限定为 `app_admin`、`app_dev`，owner 关系保持由应用创建和删除生命周期维护。
- `app_owner` 和 `app_admin` 不能通过成员管理功能操作自己的角色关系。
- “每个应用每人只能加一次”按当前关系唯一性解释：同一时刻仅允许一条应用角色关系；移除后允许重新添加。
- 每个应用最多一个 `app_owner`；正常真实用户创建流程应建立且仅建立一个 owner，技术性的 `system` 创建流程保持既有无真实 owner 兼容行为。

# Open questions

# Verification expectations

- Core 单元测试覆盖三种有效角色、无关系/非应用角色/过期关系、角色操作矩阵、分页总数、创建者 owner 写入、应用删除关系清理与事务失败。
- MVC 与 WebFlux API 契约测试验证两个应用列表入口透传同一角色过滤行为。
- MVC 与 WebFlux API 契约测试覆盖成员查询、角色分配/变更/移除及无权限响应一致性。
- SQL 资源测试验证 MySQL、H2 manifest 包含新增迁移，并验证角色代码与历史 owner 回填语句。
- 运行 TinyEngine Core、Boot 自动配置和 Starter SQL 资源相关测试。
