# TinyEngine 模板创建应用

## 模板创建输入

- 模板创建应用表单应要求用户输入新应用名称和新应用编码。
- 新应用编码不得从源模板编码复制，也不得由系统静默生成。
- 应用编码必须匹配 `^[A-Za-z0-9_-]{1,20}$`。
- 前端应在提交前校验应用编码，后端应独立执行同等格式校验，不能信任前端输入。
- 模板创建请求应把用户输入的新应用编码传递给后端并保存到新应用。

## 编码唯一性

- 新应用编码在当前租户内必须唯一。
- 后端应在创建应用记录前查询当前租户是否已有相同编码；存在时应返回稳定业务错误且不执行应用写入。
- 数据库唯一约束应继续作为并发请求的最终保护。
- 编码校验或后续复制失败时，不得留下部分应用、页面或角色数据。

## 源模板验证与读取

- 复制前应验证源应用存在、属于当前租户且具有模板标识。
- 只有源应用通过上述验证后，模板复制服务才可通过内部 Mapper 读取源模板页面。
- 内部源模板读取不要求当前用户持有源模板的应用成员角色，因为模板是当前租户内已授权的复制来源。
- 跨租户应用、非模板应用或不存在的应用不得进入内部模板读取路径。
- 目标页面应继续通过现有 PageService 创建，以保留目标应用的服务层校验和创建行为。

## 新应用角色与事务

- 真实用户通过模板成功创建应用时，应为该用户创建且仅创建一个新应用的 `app_owner` 关系。
- 新应用、页面复制和 Owner 关系创建应位于同一事务。
- 任一步骤失败时，事务应整体回滚。
- 技术性的 `system` 身份行为继续遵循 TinyEngine 应用访问规格，不在本变更中调整。

## 错误反馈

- 模板创建 API 请求失败时，应由全局 HTTP 层展示一次错误提示。
- 模板详情组件不得为同一 Promise rejection 再显示局部通知。
- 错误提示不得直接把 Error 对象作为消息文本，避免出现空白提示框。

## 兼容性

- 现有模板列表、模板详情和成功创建后的跳转行为保持不变。
- Servlet MVC 与 WebFlux 继续共享同一 Core 模板复制语义。
- 实现应兼容 Java 8。
