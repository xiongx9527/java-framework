# TinyEngine 应用级 AI 模型配置持久化设计

## 背景与目标

TinyEngine 机器人插件当前将模型服务、模型列表、默认模型和 API Key 保存在浏览器
`localStorage` 的 `tiny-engine-robot-settings` 中。该方式导致配置仅对当前浏览器可见，清理缓存后丢失，
也会把上游模型凭据暴露给前端运行时。

本次变更将模型配置持久化到 MySQL，并按 TinyEngine 应用共享。应用的 `app_owner` 和
`app_admin` 负责管理配置，`app_dev` 可以使用已启用模型，但不能查看密钥或修改配置。
API Key 使用项目现有 `fw-plus-mybatis-encrypt` 字段加密能力落库，所有上游模型调用均由
服务端完成。

## 范围

- 新增应用级模型服务和模型配置表、实体、Mapper、服务及 API。
- 使用 `@FieldEncrypt` 对模型服务实体的 API Key 字段透明加密和解密。
- MVC 与 WebFlux API 共用 TinyEngine Core 的配置服务和权限校验。
- AI 代理根据应用、服务和模型标识从数据库解析上游调用参数。
- 机器人设置页面改为读取和管理应用共享配置。
- 一次性迁移浏览器中的旧模型配置。
- 删除应用时同步删除模型配置。
- 提供 MySQL 和测试数据库的幂等建表或升级能力。

不在本次范围内：

- 租户级或用户级模型配置。
- 聊天记录的服务端持久化。
- 新增加密算法或改变 `fw.plus.mp-encrypt` 的配置契约。
- 向浏览器返回可逆密钥、密文或解密接口。

## 方案选择

采用规范化两表方案，而不是每个应用保存一份 JSON：服务级密钥可以直接使用字段加密，
模型可独立排序和启停，数据库也能表达唯一性与级联清理约束。租户级配置不符合已确认的
应用共享边界，不采用。

## 架构与职责

### TinyEngine Core

Core 负责模型配置的数据模型、Mapper、事务、应用角色校验和安全 DTO。新增的应用模型配置
服务是唯一业务入口，控制器和 AI 代理不得直接访问 Mapper。它依赖现有 `AppRoleService`，
并复用 `AppPermission` 语义：读取和使用需要应用读取/开发权限，管理需要应用管理权限。

配置服务拆分为清晰操作：

- 查询应用可用模型：Owner、Admin、Dev 均可调用，只返回调用选择所需的非敏感字段。
- 查询管理配置：仅 Owner、Admin 可调用，API Key 只返回是否存在和固定掩码。
- 新增、修改、删除服务及模型：仅 Owner、Admin 可调用。
- 导入旧配置：仅 Owner、Admin 可调用，并且只允许导入到当前租户的目标应用。
- 解析调用配置：供后端 AI 代理调用，校验当前用户可使用该应用后返回内部凭据对象。

### Boot API 层

`TinyEngineApiFacade` 暴露统一业务契约，MVC 与 WebFlux 控制器只负责请求映射、参数校验和
错误转换。两种 Web 栈必须调用同一个 Core 服务，不能复制权限或密钥处理逻辑。

建议使用以下应用资源路径；具体 Controller 可按现有前缀组合：

- `GET /apps/{appId}/ai-model-services`：获取可使用的服务和模型。
- `GET /apps/{appId}/ai-model-services/manage`：获取管理视图。
- `POST /apps/{appId}/ai-model-services`：新增服务及初始模型。
- `PUT /apps/{appId}/ai-model-services/{serviceId}`：修改服务。
- `DELETE /apps/{appId}/ai-model-services/{serviceId}`：删除服务及其模型。
- `POST /apps/{appId}/ai-model-services/{serviceId}/models`：新增模型。
- `PUT /apps/{appId}/ai-model-services/{serviceId}/models/{modelId}`：修改模型。
- `DELETE /apps/{appId}/ai-model-services/{serviceId}/models/{modelId}`：删除模型。
- `POST /apps/{appId}/ai-model-services/import-local`：一次性导入旧配置。

### AI 代理层

聊天请求不再携带 Base URL 或 API Key。前端只提交 `appId`、`serviceId`、`modelName`、消息
和现有生成参数。AI 代理通过 Core 配置服务解析内部调用配置，使用解密后的密钥请求上游。
内部凭据对象不参与 HTTP 序列化，且生命周期限制在一次调用内。

现有浏览器密钥令牌兼容逻辑仅用于迁移窗口，不再作为正常聊天链路。迁移完成后，应删除
前端通过请求体传递模型凭据的路径，避免数据库配置与客户端配置形成两个真相来源。

## 数据模型

### `t_ai_model_service`

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `tenant_id` | 租户标识 |
| `app_id` | TinyEngine 应用 ID |
| `service_key` | 应用内稳定服务标识 |
| `provider` | 服务类型或兼容协议类型 |
| `label` | 显示名称 |
| `base_url` | 上游服务地址 |
| `api_key` | 加密后的 API Key，可空 |
| `allow_empty_api_key` | 是否允许无密钥调用 |
| `enabled` | 是否启用 |
| `sort_order` | 排序 |
| `created_by/created_time` | 创建审计字段 |
| `last_updated_by/last_updated_time` | 更新审计字段 |

实体的 `apiKey` 是 `String`，标注
`com.xiongx9527.fw.plus.common.mate.annotation.FieldEncrypt`。数据库列必须能容纳算法输出，
不能按明文 Key 的长度估算。应用内 `service_key` 唯一，唯一键同时包含 `tenant_id` 和
`app_id`，确保租户隔离。

### `t_ai_model`

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `tenant_id` | 租户标识 |
| `app_id` | 应用 ID，便于隔离校验和应用删除 |
| `service_id` | 所属模型服务 |
| `name` | 上游模型名称 |
| `label` | 显示名称 |
| `capabilities` | 非敏感能力配置 JSON |
| `enabled` | 是否启用 |
| `sort_order` | 排序 |
| 审计字段 | 与服务表一致 |

同一服务内 `name` 唯一。服务删除时由业务事务显式删除模型；数据库外键可作为补充约束，
但不能替代业务层的租户和权限校验。

应用的默认模型、快捷模型、聊天模式和思考开关是应用共享行为配置，随服务配置一并持久化。
这些非敏感设置统一保存在现有 `App.extendConfig` 的 `aiModelSettings` 命名空间，不新增第三张表，
也不把应用设置塞入任一服务记录。默认模型和快捷模型引用 `service_key + model name`；引用失效时
返回未配置状态，不静默切换到其他模型。更新该命名空间必须由模型配置服务完成，并保留
`extendConfig` 中其他业务键。

## 字段加密

TinyEngine 模块引入并启用现有 `fw-plus-mybatis-encrypt` 能力。由于当前持久层使用
MyBatis-Plus，运行时同时保留 MP 字段名解析适配器。写入 INSERT/UPDATE 前由
`FieldEncryptInterceptor` 加密，查询结果由 `FieldDecryptInterceptor` 解密；业务代码不手动
调用加解密器，也不进行二次加密。

部署必须通过外部配置提供 `fw.plus.mp-encrypt.private-key`、IV、盐值和算法等参数。真实密钥
不得进入源码、初始化 SQL、前端构建产物、日志或设计文档。生产环境缺少加密配置时，应用
应启动失败或禁用模型配置写入，不能以明文降级。

DTO 与实体严格分离：实体仅停留在 Mapper/Service 内部；HTTP 响应 DTO 不包含 `apiKey`
字段，只包含 `hasApiKey` 和固定掩码。掩码不得根据密钥长度或内容生成。

密钥更新采用三态语义：

- 请求未提供或提供空白 `apiKey`：保留数据库原值。
- 请求提供非空 `apiKey`：替换原值，拦截器负责加密后写入。
- `clearApiKey=true`：显式清空；与非空 `apiKey` 同时出现时拒绝请求。

## 权限与隔离

| 操作 | `app_owner` | `app_admin` | `app_dev` |
| --- | --- | --- | --- |
| 使用已启用模型 | 允许 | 允许 | 允许 |
| 查看非敏感可用模型列表 | 允许 | 允许 | 允许 |
| 查看管理配置 | 允许 | 允许 | 禁止 |
| 新增、修改、删除配置 | 允许 | 允许 | 禁止 |
| 导入旧配置 | 允许 | 允许 | 禁止 |

每次操作均以后端当前登录用户为准，并同时校验 `tenant_id`、`app_id` 和应用角色。客户端提交
的租户、角色、Base URL 或密钥都不能作为授权依据。查询服务下模型、修改模型和发送消息时，
均需确认服务和模型属于请求路径中的同一应用，防止通过 ID 猜测跨应用访问。

## 请求数据流

### 管理配置

1. 前端从当前路由取得应用 ID，请求管理接口。
2. Core 校验当前用户为该应用 Owner 或 Admin。
3. Mapper 查询实体，MyBatis 解密拦截器可能在内部恢复密钥。
4. Service 立即映射为安全 DTO，仅计算 `hasApiKey`，不复制密钥。
5. 前端展示掩码；保存时按密钥三态语义提交。

### 发送消息

1. 前端提交应用 ID、服务 ID、模型名称和消息，不提交模型凭据。
2. Core 校验用户拥有该应用的可使用角色，并确认应用、服务和模型均已启用。
3. Core 从数据库读取配置，MyBatis 在服务端解密 API Key。
4. AI 代理规范化 Base URL，使用内部凭据调用上游并流式返回响应。
5. 上游鉴权或可用性错误转换为模型调用错误，不清除 TinyEngine 登录状态。

## 旧配置迁移

只有 Owner 或 Admin 首次进入应用，且数据库没有任何模型服务时，前端才提示导入浏览器中的
`tiny-engine-robot-settings`。Dev 不显示提示，也不能调用导入接口。

迁移规则：

1. 前端解析并校验现有设置版本，只发送模型服务、模型和应用级行为配置。
2. 后端再次校验管理权限，并在单一事务中校验全部数据后批量写入。
3. 任意记录无效、重复或写入失败时整体回滚，浏览器旧配置保持不变。
4. 数据库已有配置时返回冲突，不自动覆盖。
5. 全部成功后，前端仅删除旧设置中的模型配置；聊天记录和无关本地设置保留。

为避免多个应用误领同一份旧配置，成功迁移后即移除旧模型配置。后续应用不会再次自动导入。
迁移接口是过渡能力；完成兼容周期后可移除，但数据库配置格式保持不变。

## 删除与一致性

服务及其模型的新增、修改、删除和迁移均使用事务。删除服务时先删除其模型，再删除服务。
删除应用时，在现有 `AppServiceImpl.deleteAppById` 事务内调用模型配置服务清理两张表，随后
继续删除角色和应用；任一步失败则整个应用删除回滚。

重复服务、重复模型由业务校验和数据库唯一约束共同保证。并发写入最终以唯一约束为准，
统一转换为可读的冲突错误。

## 错误与日志

- 未登录或登录令牌失效：401，前端按现有规则进入登录页。
- 已登录但应用权限不足：403，不清除登录状态。
- 应用、服务或模型不存在：404；跨租户资源同样按不可见处理。
- 数据库已有配置、服务或模型重复：409，并返回稳定业务错误码。
- 参数无效或密钥三态冲突：400。
- 上游鉴权、限流、超时或服务错误：转换为模型调用错误，保留当前登录状态。

日志只记录请求追踪号、应用 ID、服务 ID、模型名和错误类型。禁止记录 API Key、认证请求头、
包含密钥的请求体、解密实体或完整上游错误响应。异常对象若可能携带上游请求，也必须先脱敏。

## 前端行为

- 模型设置入口继续使用当前 TinyEngine 工作界面，只在选定应用后可用。
- Owner、Admin 可见管理控件；Dev 只看到模型选择，不显示配置入口和管理命令。
- 列表和选择项来自数据库接口，不再以 `localStorage` 作为正常数据源。
- 配置保存后刷新当前应用的模型状态，不刷新整个应用中心。
- 同一次失败只显示一条明确错误，不能由全局拦截器和组件重复弹框。
- 未配置默认模型、默认模型已停用或引用失效时，禁止发送并提示选择模型。

## 初始化与兼容

- MySQL 初始化 SQL 和升级逻辑必须幂等，保留本机现有 TinyEngine 数据。
- 测试数据库提供等价表结构和约束。
- 所有 Java 实现兼容 Java 8，不使用 Java 9 及以上 API。
- 现有已部署实例升级时，先配置字段加密参数，再执行建表和应用升级。
- 不迁移或重写现有 `t_model`；该表是 TinyEngine 应用数据模型，与 AI 模型配置无关。

## 测试与验收

### Core 单元及集成测试

- Owner、Admin 可管理，Dev 只能使用；无角色用户不可读取或使用。
- 同一 ID 在不同租户或应用下不能互相访问。
- 服务和模型唯一约束、启停状态及应用删除级联正确。
- 密钥留空保留、非空替换、显式清除和冲突请求均符合三态语义。
- H2/MySQL 集成测试证明 INSERT 后数据库原始列不是明文，正常查询后业务层获得可用明文。
- 安全 DTO、序列化结果、日志和异常中均不包含明文或数据库密文。

### API 与 AI 测试

- MVC 与 WebFlux 对同一请求返回一致的状态码和安全响应结构。
- 聊天请求不接受客户端 Base URL/API Key 作为调用依据。
- Dev 能通过已保存配置发送消息，但不能访问管理接口。
- 上游 401/403、429、超时和 5xx 不会触发 TinyEngine 退出登录。
- 模型不存在、被停用或不属于当前应用时拒绝调用。

### 前端测试

- 三种角色的入口、按钮和可用操作符合权限矩阵。
- 数据库为空时可迁移，已有配置时不覆盖，失败时保留本地旧配置。
- 迁移成功仅移除旧模型配置，不删除聊天记录。
- 页面刷新、换浏览器或同应用其他成员登录后仍能看到相同模型配置。
- API 错误只弹一次，配置或聊天错误不会错误跳转登录页。

### 部署验收

- 使用占位测试密钥创建配置，直接查询数据库确认列为密文。
- Owner、Admin、Dev 分别完成权限验证。
- 使用另一个浏览器或账号打开同一应用，确认模型配置共享且密钥不可见。
- 删除测试应用后，两张 AI 模型配置表中不存在其记录。
- 构建并部署 TinyEngine Starter，验证本机 19080 样例和 MySQL 现有数据不受损。

## 交付约束

- 不提交真实 API Key、加密主密钥或构建产物。
- 实现按数据层与加密、API 与权限、AI 调用链、前端与迁移、部署验证分阶段提交。
- 不混入工作区其他未完成改动。
