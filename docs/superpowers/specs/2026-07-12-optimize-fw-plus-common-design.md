# optimize-fw-plus-common 技术设计

## 背景

`fw-plus-common` 是 Core 层公共基础模块，承载校验、线程上下文、异常、结果封装、Web/Spring 工具等跨模块能力。它的调用方分布在 Boot、POI 等模块，优化时必须优先保证兼容性，避免为了“看起来更干净”扩大回归面。

本次设计采用“兼容收敛”：只处理有明确代码证据、能验证收益的优化点。无证据、无收益或只属于风格偏好的改动不做。

## 目标

- 降低 `fw-plus-common` 中重复、低收益复杂度和潜在运行风险。
- 保持既有 public API 的方法签名、返回语义和异常语义兼容。
- 优先删除无效代码、复用已有实现、简化公共路径。
- 对非平凡逻辑改动补充最小测试或最小下游验证。

## 非目标

- 不新增业务能力。
- 不引入新依赖。
- 不做跨模块架构重写。
- 不批量格式化或纯风格化修改。
- 不做需要独立迁移计划的 public API 清理。

## 技术方案

### 1. 优化点筛选

先用 CodeGraph 和必要的源码阅读确认每个候选点：

1. 所在类和方法是否属于公共调用路径。
2. 是否存在重复逻辑、无效包装、可删除代码、异常吞噬、线程上下文泄漏或明显低收益复杂度。
3. 是否能用最小测试或现有下游测试验证。

不满足上述条件的候选点不进入实现清单。

### 2. 实现优先级

采用以下顺序，命中上层就停止，不继续加复杂度：

1. 删除无效代码。
2. 复用模块内已有工具或模式。
3. 使用 JDK 或已安装依赖的现有能力。
4. 做最小兼容改动。

不得新增单实现接口、工厂、配置项或“以后可能用到”的抽象。

### 3. 兼容边界

默认保持以下内容不变：

- public 方法签名。
- 返回值语义。
- 异常语义。
- Maven 坐标和依赖关系。
- 下游模块已依赖的调用方式。

如果发现必须改变上述任一项，本 change 不直接处理，记录为后续独立 change。

### 4. 重点候选区域

设计阶段确认的优先探索区域：

- `CommonsValidator`：校验结果转换、异常包装、反射读取 validator context 的公共路径。
- `CommonsValidatorHolder`：线程上下文初始化、清理和空值处理。
- Web/Spring 工具类：请求上下文、Bean 获取、空值处理和异常边界。
- 异常/结果封装：重复包装、低价值分支和调用语义一致性。

具体实现阶段只处理筛选后仍有明确收益的点。

## 风险与缓解

- 公共工具隐式调用方多 → 修改前确认调用半径，修改后运行最小相关测试。
- 兼容边界限制优化深度 → 深层 API 清理留给后续独立 change。
- 测试覆盖不足 → 对被改动的分支、状态、异常或校验语义补最小测试。
- “优化”范围容易膨胀 → 没有明确证据和验证路径的改动不做。

## 测试策略

- `fw-plus-common` 内部：为被改动的非平凡逻辑补最小单元测试。
- 下游调用方：触及 `CommonsValidator`、`CommonsValidatorHolder` 等公共路径时，运行 Boot/POI 中对应最小测试或编译验证。
- 构建命令优先限定模块范围，避免无关全量构建。

## 验收标准

- OpenSpec `common-module-optimization` 的兼容、证据驱动和最小验证要求均满足。
- 所有实现任务都有明确收益说明或代码证据。
- 非平凡逻辑改动有最小可运行验证。
- 没有新增依赖、无 public API 语义变化、无无关格式化改动。
