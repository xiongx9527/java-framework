**关键发现（既有缺陷，本轮顺手修掉）**
WS 配置读取走 `MagicBaseService#getConfigValue` 的 `configMap.get("token.secret")` 这类**点号扁平键**，但 `MagicAPIWsConfig extends HashMap<String,Object>`，
Spring Boot 把嵌套 YAML（`fw.plus.ws.token.secret`）绑定进 `Map<String,Object>` 时得到的是**嵌套 Map**（`{token={secret=...}}`），
扁平键取不到值 → `getWebsocketPath()` 回落 `/ws/api`、`getTokenExpireHours()` 回落 2、`getTokenSecret()` 抛异常。
该缺陷与前缀无关，旧前缀下同样存在（`git log` 显示相关文件仅有一次包重命名提交，属长期存在）。
修法（最小、仅限 ws 包）：`MagicAPIWsConfig.flatten()` 递归把嵌套 Map 展开为点号扁平键，`getConfig()` 返回展开结果。未触碰共享 `MagicBaseService`。

**验证方式（可复用）**
`/tmp/ws-checks/c1..c7.sh` 7 项 Runtime 检查：全层 install、样例编译、依赖树、starter 结构与登记、POM 依赖集合、前缀静态+元数据、前缀运行时。
C7 用**真实 SpringApplication + 真实 application.yml**（`/tmp/ws-prefix-runtime-check/`）分别以新/旧前缀提供同一组配置，断言读取生效/回落默认值，
并打印扁平键与嵌套键形态作为诊断。结果：8/8 验收通过（iteration 2 修复后 pass）。

**踩坑**
- `comet native next` 无 `--validate-only`（0.4.0-rc.1）；`builder-handoff` 必须带 `review{status,summary,reviewer_execution_ref}`；
  检查回执**不含 stdout**，只含 argv/status/exit_code/duration。
- 修复后 Runtime 要求再跑一轮「final full verification」（`next_action=run-final-full-verification`），此时会**复用已有检查回执**。

**遗留（与本 change 无关）**

## change: ws-module-extraction（Comet Native，接续上一 change）

**目标**：把 magic-api WS 插件里与 magic 无关的「WebSocket 地基」抽成独立模块，使非 magic 应用可直接用 WS；magic 侧通过 SPI 接入。

**结论**：build → verify 一轮通过，`verification_result=pass`，acceptance 4/4，stateVersion 5，停在 `await-user`（等用户 accept-result）。

**新模块**：`fw-plus-boot/fw-plus-boot-project/fw-plus-boot-autoconfigure-web`（包 `com.xiongx9527.fw.plus.boot.autoconfigure.web`，地基在 `.web.ws`）。
依赖 `fw-plus-common`（**不是** `fw-plus-boot-common`，后者会拖进 magic）。依赖方向 `fw-plus-boot-autoconfigure` → `autoconfigure-web`（optional）。

**SPI**：`WsBusinessDispatcher`(existsApp/findEnabledSubscribes/execute)、`WsSubscribeScript`、`WsInvocationContext`(INIT/MESSAGE/CLOSE + getReplyHandle)、`WsReplyHandle`、`WsBasePathProvider`、`WsHandshakeInterceptor`。
`AbstractWebSocketHandler` = 原 `BaseDynamicWebSocketHandler` 的地基部分；`SimpleWebSocketHandler`/`RedisWebSocketHandler` = 原 `Simple/RedisDynamicWebSocketHandler`。

**magic 侧**：`BaseDynamicWebSocketHandler` 改为 `implements WsBusinessDispatcher, BaseService`（不再是 handler）；删除 `Simple/RedisDynamicWebSocketHandler`、`MagicAPIWsHandlerConfiguration`、`MagicAPIWsConfig`；`MagicAPIWsConfiguration` 不再实现 `WebSocketConfigurer`。**包名与前端资源零改动**（`WsModule` FQN 不变，前端 `magic-ws-datasource.js` + `dist/*.iife.js` 均按原名引用，git 确认未改）。

**本轮修掉的两个真实缺陷（都在 `WsRedisConfiguration`）**
1. `redisMessageListenerContainer` 上的 `@DependsOn("redisWebSocketHandler")`：宿主自备 handler 时该 Bean 被 `@ConditionalOnMissingBean` 跳过 → 容器启动直接 `NoSuchBeanDefinitionException`。改为 `getBeanProvider(AbstractWebSocketHandler.class).getIfAvailable()` + `instanceof RedisWebSocketHandler` 判断，移除 `@DependsOn`。
2. `redisMessageListenerContainer` 补 `@ConditionalOnMissingBean`，与同文件 `redisWebSocketHandler` 的扩展点对齐（也让测试可注入不自动启动的子类）。

**解除 E4 硬阻塞**：删除两个孤儿 mqtt 测试（`MagicMqttDashboardControllerTest`、`MqttDashboardServiceTest`）。它们 import 的 `magicapi.plugin.mqtt.model|service|web` 在仓库中不存在（真实类是 `plugin.mqtt.server.model|service`），是历史提交遗留的死测试且阻塞 `testCompile`。删除后 `mvn -o -pl fw-plus-boot-autoconfigure -am test` **原样跑通 636 测试**，不再需要「临时把 mqtt 目录移走」这种手法。文件由 git 跟踪可恢复。

**A3 覆盖补强（新增 11 个测试，新模块 24 → 35）**

## change: ws-module-extraction 修订（用户改口径：废弃新模块 → 包级隔离）

**用户指令链**：「本机安装了docker」→「不是单独建一个 fw-plus-boot-autoconfigure-web 工程啊」→ 落点确认为 `fw-plus-boot-autoconfigure` 的 `com.xiongx9527.fw.plus.boot.autoconfigure.web` 包 →「改口径，包级隔离」→「fw-plus-boot-autoconfigure-web 模块废弃。」

**更正上一节最后一条错误结论**：本机**有** Docker（`/usr/local/bin/docker` → `/Applications/Docker.app`，daemon 用 `open -a Docker` 拉起，本地已有 `redis:7-alpine` 镜像）。上一轮「本机无 docker、真实 Redis 与真实 HTTP Upgrade 跑不通」的判断是**错的** —— 沙箱重写了 PATH，`which docker` 因此失败。真实 Redis 跨实例广播（`WsRedisBroadcastEndToEndTest` 4 例）与真实 HTTP Upgrade（`WsEndpointHttpUpgradeTest` 2 例）本次均已跑通。

**落地形态**：15 主类 + 8 测试类从废弃模块迁入 `...autoconfigure.web.ws` 包（包名不变 → Java 代码零改动）；`spring.factories` 追加 2 条；回退 4 处 POM（聚合 / BOM / autoconfigure / starter）；删除模块目录（`git ls-files` = 0，全仓零引用）。

**迁移暴露并修掉的 3 个问题（只在「同模块」这个落点下才出现）**
1. **多重 SLF4J 绑定**：`fw-plus-boot-autoconfigure` 自身 optional 依赖链上有 3 个 SLF4J 绑定 —— Spring Boot 的 `logback-classic`、`pulsar-client`/`pulsar-client-admin` 的 `log4j-slf4j-impl`、`seata-server` 的 `slf4j-reload4j`。任何起真实 Spring 上下文的测试都会在启动期抛 `LoggerFactory is not a Logback LoggerContext but Logback is on the classpath`。**排查教训：逐个排除就是打地鼠** —— 剔掉 `log4j-slf4j-impl` 后 `slf4j-reload4j` 立刻接棒抛同一断言（错误文案里换的只是 jar 名）。正确做法是**一次列全所有绑定**再统一排除：`mvn dependency:tree | grep -E 'slf4j-(reload4j|log4j12|simple|jdk14|nop|impl)|logback-classic'`。
2. **`@EnableAutoConfiguration` 语义随落点变了**：测试里「最小应用」原先靠「独立模块的 spring.factories 只有 2 条」间接成立；并入后同一注解会拉起本模块的 16 条自动配置，其中 magic-api 的 vue3 插件在 `magic-api.web` 缺省时把过滤器 url-pattern 拼成 `null/vue3/component/*` → Tomcat 启动失败（与该测试被测能力无关）。改为 `@ImportAutoConfiguration({...})` 显式导入，反而更贴合「只引入 WS 自动配置即可用」的验收口径。
3. **少 `WebSocketServletAutoConfiguration` 会 500**：Tomcat 能起、请求能到 DispatcherServlet，但 Upgrade 返回 500，根因是 `No 'javax.websocket.server.ServerContainer' ServletContext attribute` —— 该自动配置提供的 `WsSci` 才装上 JSR-356 容器。三条标准自动配置各管一段：`DispatcherServletAutoConfiguration` 让请求过 HandlerMapping、`ServletWebServerFactoryAutoConfiguration` 提供内嵌 Tomcat、`WebSocketServletAutoConfiguration` 装 `WsSci`。

**检查脚本（新口径，`/tmp/ws-verify/`）**：`lib-redis.sh`（幂等保障 Docker + Redis 容器，被 C3/C4 source）、`c1-compile.sh`（全量编译 + 无独立 WS 模块）、`c2-isolation.sh`（纯静态包级隔离，不再查依赖树）、`c3-web-tests.sh`（ws 包定向测试 + 真实 Redis/HTTP Upgrade 不许跳过 + 选择器不越界到 magic 包）、`c4-magic-tests.sh`（整模块不许回退）、`c5-structure.sh`（结构不变 + 无废弃模块残留，grep 需排除 `.git`/`target`/`docs`）。
